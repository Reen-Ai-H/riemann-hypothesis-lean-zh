# 04 · 如何自己验证

> 这一篇面向想亲手跑一遍的人。即使不跑，读完也能明白"验证一份 Lean 证明"具体指什么。

## 验证清单

| 步骤 | 做什么 | 回答的问题 | 难度 |
|---|---|---|---|
| ① 来源校验 | 比对 SHA-256 | 我拿到的代码是作者发布的原版吗？ | 简单，几分钟 |
| ② 陈述审查 | 读 `Main.lean`、`Statements.lean` | 它证明的真的是黎曼猜想吗？ | 简单，见 [03 篇](03-Lean陈述逐行解读.md) |
| ③ 静态扫描 | 全文搜索 `sorry`、`axiom` 等 | 有没有明显"作弊"的地方？ | 简单，几分钟 |
| ④ 完整编译 | `lake build Main` | Lean 内核接受这个证明吗？ | **极难**，需要大型服务器和很长时间 |
| ⑤ 公理审计 | `#print axioms` | 证明有没有依赖额外的假设？ | 编译完后几分钟 |
| ⑥ 独立重放 | `lean4checker` 等外部检查器 | 结果是否依赖了项目里的元程序或编译器？ | 中等 |

---

## ① 来源校验

本仓库 `src/` 与作者在 alpo.ge 发布的压缩包**逐字节一致**（2026-11-21 核对），只额外加了 README、`docs/`、`scripts/`、`Check.lean`、`SHA256SUMS`、`.gitignore` 和 `original/README.md`。

自己复核：

```bash
bash scripts/fetch-original.sh --lean
```

脚本会从 alpo.ge 下载 14 个分卷，核对哈希，解压后与本仓库的 `src/` 做 `diff`。完整压缩包的哈希应为：

```
9631b4f020199e580ba86178cb56c6e9b09f690c2369a80dc4334aa93f49c7fc  lean.tar.gz   (239,275,554 字节)
```

## ② 陈述审查

见 [03 篇](03-Lean陈述逐行解读.md)。要点：`riemannHypothesis` 的类型是 **Mathlib 自带的** `RiemannHypothesis`，可在 Mathlib 固定版本里核对：

<https://github.com/leanprover-community/mathlib4/blob/0df444a360eaa60ab8c11dca51a86af692955474/Mathlib/NumberTheory/LSeries/RiemannZeta.lean#L185>

## ③ 静态扫描

```bash
grep -rlw sorry src | wc -l          # 应为 0
grep -rlw admit src | wc -l          # 应为 0
grep -rlE '^\s*axiom ' src | wc -l   # 应为 0
grep -rl native_decide src | wc -l   # 应为 0
```

已公开的扫描结果（两家独立统计，口径略有不同）：

| 检查项 | 结果 |
|---|---|
| `sorry` / `admit` | 0 |
| `axiom` 声明 | 0 |
| `native_decide`、`ofReduceBool`、`trustCompiler` | 0 |
| `implemented_by`、`extern`、`unsafe`、`opaque` | 0 |
| `debug.skipKernelTC` | 0 |
| 自定义 `macro` / `elab` / `run_tac` 等 | 有若干处，经人工查看为策略缩写和命名空间设置 |
| `addDecl` | 1–2 处（`CutCptCopy.lean` 中用于复制已有声明，仍经过内核检查） |

静态扫描只能排除明显问题，不能代替 ④⑤⑥。

## ④ 完整编译

```bash
# 1. 安装 elan（Lean 版本管理器）
curl https://elan.lean-lang.org/elan-init.sh -sSf | sh -s -- -y
source ~/.elan/env

# 2. 克隆本仓库（约 1.3 GB）
git clone --depth 1 https://github.com/Reen-Ai-H/riemann-hypothesis-lean-zh.git
cd riemann-hypothesis-lean-zh

# 3. 下载 Mathlib 预编译缓存（lake-manifest.json 已固定版本）
lake exe cache get

# 4. 先编译陈述文件（很快），再编译主定理的全部依赖
lake build Statements
lake build Main
```

项目配置：

| 项 | 值 |
|---|---|
| Lean 版本 | `leanprover/lean4:v4.33.1` |
| Mathlib | `0df444a360eaa60ab8c11dca51a86af692955474` |
| 全局选项 | `maxHeartbeats = 4000000`，`autoImplicit = false`，`--tstack=400000` |

**资源预期**：这是 1700 多万行代码的编译。一个独立验证项目在 128 核、503 GB 内存的机器上，开始阶段速度约为每分钟 400 个模块，预估要 7 小时以上。普通笔记本电脑基本不可行。

## ⑤ 公理审计

编译成功后，运行本仓库根目录的 `Check.lean`：

```bash
lake env lean Check.lean
```

合格的输出，每个定理后面只应列出 Lean 的三条标准公理：

```
'riemannHypothesis' depends on axioms: [propext, Classical.choice, Quot.sound]
```

如果出现 `sorryAx`（有未完成的证明）、`Lean.ofReduceBool`（信任了编译器求值）或任何自定义公理，就说明证明并不完整。

## ⑥ 独立重放

用 [lean4checker](https://github.com/leanprover/lean4checker) 等外部工具重新检查编译出的环境，确认结果不依赖 Lean 的前端（elaborator）或项目里的任何元程序。这一步主要防范的是"自定义策略绕过了检查"这类罕见情况。
